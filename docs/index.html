A Python framework for screen-driven game automation. It captures a rectangle of your screen, detects the obstacle in it, asks a TypeSafe System One model for exactly one action, then decides whether that action is allowed to reach the keyboard. The first run is a headless simulator — no display, no API key, no game.

World 1-1 · Overview

A framework, not a cheat

Roughly 900 lines of Python across five modules, MIT licensed. Every stage has a simulated implementation and a native one behind the same interface, which is why the whole loop runs on a machine with no display, no API key and no game attached to it.

  • ?Headless simulator mode with a moving obstacle
  • ?TypeSafe System One Choice integration through TypeSafeClient.system_one()
  • ?Native mss capture and OpenCV detector scaffolding
  • ?Simulator, observation-only and pynput input controllers
  • ?Profile-based monitor, detector, HSV, model, confidence and key settings
  • ?Bounded latest-state handoff between capture and decision loops
  • ?Confidence gating, action cooldowns, emergency stop and shutdown cleanup
  • ?Human-readable and JSON Lines telemetry
  • ?Dependency-free unit tests for the core behaviour

And what it isn't

This is a reusable framework, not a plug-and-play bot for every game. Supporting a real game still takes a calibrated screen region, a detector that understands that game's visuals, a profile mapping actions to controls, a confidence and timing policy tested against real outcomes, and a machine whose display and input the runtime is allowed to touch.

The simulator is fully usable in a Codespace. Native mode and live model calls need the environment above, and the full capture-to-keypress path has to be measured on target hardware rather than assumed.

World 1-2 · Pipeline

One tick, start to finish

Three modules do the work and bot.py holds them together. Each box below is a real stage in the loop, in the order it happens.

  1. PLAYER 1You pick the screen region and the keys.
  2. CAPTUREThe monitor rectangle is grabbed at 100 Hz.
  3. DETECTThe frame becomes distance, lane and speed.
  4. DECISIONThe model answers with one of four actions.
  5. CONFIDENCEAnything under the floor becomes DO_NOTHING.
  6. SAFETYCooldowns, timeouts and the stop file get a veto.
  7. ACTIONOne key event, or a logged refusal.

  1. See vision.py

    GameVision grabs a monitor rectangle with mss and hands the frame to a detector. GreenObstacleDetector converts to HSV, masks the configured colour range, zeroes everything above the ROI line, takes the largest contour at or over min_area, and measures distance from the right edge of the frame to the obstacle's centre.

    native
    threat_distance=… lane_position=… speed=… threat_visible=…
    simulator
    Obstacle in Center lane, distance: … px

  2. Think decision.py

    TypeSafeDecisionProvider wraps the published SDK: it builds a Choice over JUMP, DODGE_LEFT, DODGE_RIGHT and DO_NOTHING, calls TypeSafeClient.system_one() with the state string, and rejects any answer outside that set. SimulatorDecisionProvider answers the same question locally with a distance rule, so simulator mode needs no network or key.

    returns
    action · confidence · per-option probabilities

  3. Act input.py

    Three backends share one interface. SimulatorController prints the key it would press. NullController suppresses everything, which is what --observe-only selects. PynputController maps the action to a real key through the profile and presses it, tracking held keys so shutdown can release them.

    result
    one key event, or a logged refusal

bot.py underneath it all Capture and decisions run on separate threads at separate rates. A one-slot LatestStateQueue sits between them: a new state overwrites the old one instead of queueing, so a slow decision can never build a backlog of stale frames. A dropped state is counted, not hidden.

World 1-3 · Safety

Refusing to act is a feature

A bot with a keyboard needs more ways to do nothing than to do something. Four of these gates can withhold a key press; the last two are how you see it happen.

  1. DECISIONThe provider returns an action, a confidence and probabilities.
  2. CONFIDENCE CHECKBelow --min-confidence it is replaced with DO_NOTHING at confidence 0, tagged low_confidence.
  3. COOLDOWN / SAFETYActionLimiter.allows() and the stop event can still withhold the key.
  4. ACTIONThe controller presses the mapped key, or the refusal is printed and counted.

Confidence gating

Any decision under --min-confidence is replaced with DO_NOTHING at confidence 0 and tagged low_confidence. The profile sets the default; the flag overrides it.

Cooldowns

ActionLimiter enforces a minimum gap between any two key events (--min-action-interval, default 0.05 s) and a longer gap before repeating the same one (--action-cooldown, default 0.15 s). DO_NOTHING is always allowed through.

Emergency stop

Ctrl+C, SIGTERM, or the appearance of the file named by --stop-file sets the stop event. A capture failure or a native key failure sets it too. On the way out, every held key is released.

Timeouts and fallbacks

A decision that overruns --decision-timeout doesn't block the loop — the tick falls back to DO_NOTHING and records why: decision_timeout, decision_in_flight, or the exception class the provider raised.

Telemetry

Every tick prints action, confidence, probabilities, engine_latency_ms, state_age_ms, whether the key went out, and the fallback reason. --jsonl emits the same record as one JSON object per line for scripts.

Shutdown counters

The run ends with a [STATS] line: captures, capture errors, decisions, fallbacks, actions sent, actions blocked and states dropped. Blocked and dropped are the two worth watching.

World 1-4 · Profiles

One JSON file per game

Profiles keep game-specific detail out of the loop. profiles.py validates every field on load, so a bad monitor rectangle or an unmappable key fails at startup instead of halfway through a run. Pick a field to see where it lands.

profiles/example_runner.json 
{
  "name": "example-runner",
  "model": "jev-latest",
  "min_confidence": 0.0,
  "monitor": {"left": 0, "top": 0, "width": 1280, "height": 720},
  "actions": {
    "JUMP": "space",
    "DODGE_LEFT": "left",
    "DODGE_RIGHT": "right",
    "DO_NOTHING": "none"
  },
  "detector": "green_obstacle",
  "detector_config": {
    "hsv_lower": [35, 90, 140],
    "hsv_upper": [90, 255, 255],
    "min_area": 12,
    "roi_top_fraction": 0.333
  }
}

World 1-6 · First run

Start in the simulator

Clone, run the simulator, then read the telemetry. The simulator is the right first run, including in a Codespace terminal: it needs no display, keyboard permission, API key, OpenCV, mss or pynput. The commands below are shown for you to copy and run yourself — this page executes none of them.

1 · Clone it and make an environment

git clone https://github.com/ojas-mohbansi/system1-gamebot.git
cd system1-gamebot
python -m venv .venv
source .venv/bin/activate

Nothing is installed yet. Simulator mode needs no third-party packages at all.

2 · Run the simulator

python bot.py --sim

This runs in your terminal, not in this page. You get simulated actions, confidence values, latency, fallbacks, and a [STATS] summary when you stop it with Ctrl+C.

3 · Point it at a profile

python bot.py --sim --profile profiles/example_runner.json

profiles/example_runner.json is checked in. Without --profile the runtime uses the defaults in profiles.py.

4 · Inspect the output

python bot.py --sim --observe-only
python bot.py --sim --jsonl

--observe-only still decides and logs but swaps in NullController, which prints [OBSERVE ONLY] Suppressed … instead of pressing anything. --jsonl emits one JSON object per decision for scripts.

5 · Tune the loop

python bot.py --sim \
  --capture-hz 100 \
  --decision-hz 10 \
  --decision-timeout 0.2 \
  --min-confidence 0.90

These are the defaults, written out. Safety flags work the same way: --action-cooldown, --min-action-interval, --stop-file.

Beyond the simulator

When you move to a real machine

Native mode needs a graphical session, input permission and the pinned packages: mss, opencv-python-headless, pynput and typesafe-sdk. Check the environment before you start the bot. 

python -m pip install -r requirements.txt
export TYPESAFE_API_KEY="your-api-key"
python bot.py --preflight \
  --profile profiles/example_runner.json

Preflight reports display, monitor count, OpenCV version and keyboard access. A headless container fails it — that's expected, and it's what --sim is for. Once it passes, run with --observe-only before you let it press anything. 

python -m unittest discover -s tests -v

The tests need no third-party packages. CI runs the same ones on every push.
